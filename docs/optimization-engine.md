# Optimization Engine Documentation

## GCP Cost Optimizer for Kubernetes

This document explains the optimization logic implemented by the GCP Cost Optimizer for Kubernetes.

The optimization engine takes Kubernetes resource requests and observed Prometheus utilization, identifies potential over-provisioning, calculates resource waste, estimates potential monthly savings, assigns priorities, and generates actionable recommendations.

The current implementation is designed and validated in a local Kubernetes environment using mock GCP cost data.

---

# 1. Optimization Engine Overview

The optimization engine is the decision-making layer of the project.

Its purpose is to answer:

> Which Kubernetes workloads appear to be using significantly fewer resources than they have requested, and what optimization opportunities can be recommended?

The engine does not directly depend on raw Kubernetes or Prometheus queries.

Instead, the Metrics Analyzer first normalizes the collected data and passes structured optimization opportunities to the engine.

The overall flow is:

```text
Kubernetes Resource Requests
            +
Prometheus Resource Usage
            |
            v
      Metrics Analyzer
            |
            v
    Utilization Analysis
            |
            v
 Over-Provisioning Detection
            |
            v
       Waste Analysis
            |
            v
    Savings Calculation
            |
            v
   Recommendation Engine
            |
            v
     Priority Scoring
            |
            v
    Optimization Report
```

---

# 2. Optimization Engine Responsibilities

The `CostOptimizationEngine` is responsible for:

* Analyzing resource waste
* Calculating CPU waste
* Calculating memory waste
* Estimating monthly savings
* Generating recommendations
* Assigning implementation priorities
* Calculating recommendation priority scores
* Creating machine-readable optimization reports
* Creating human-readable optimization reports

The implementation is located in:

```text
src/optimizer_engine.py
```

# 3. Inputs to the Optimization Engine

The engine primarily receives optimization opportunity data generated by the Metrics Analyzer.

A typical opportunity contains:

```text

memory_request

cpu_utilization_percent
memory_utilization_percent

```

Example:

```text

    "namespace": "default",
    "name": "web-app-79bc9f6b6c-td285",
    "cpu_request": 1.0,

    "average_utilization_percent": 0.34,
    "reason": "Resource utilization below 30%"
}
```

The optimization engine does not need to query Prometheus again because the Metrics Analyzer has already prepared the utilization data.

---

# 4. Resource Utilization

The first stage of the optimization workflow is understanding how much of the requested resource a workload is actually using.

The basic calculation is:

```text
Utilization % =
(Actual Usage / Resource Request) × 100
```

CPU and memory are calculated independently.

---

## CPU Utilization

For example:

```text
CPU Request = 1.0 core
CPU Usage   = 0.01 core
```

Therefore:

```text
CPU Utilization =
(0.01 / 1.0) × 100

= 1%
```

---

## Memory Utilization

For example:

```text
Memory Request = 2.0 GB
Memory Usage   = 0.02 GB
```

Therefore:

```text
Memory Utilization =
(0.02 / 2.0) × 100

= 1%
```

The actual values are collected dynamically from Prometheus, so they can change between executions.

---

# 5. Average Utilization

The engine also uses an average of CPU and memory utilization.

Conceptually:

```text
Average Utilization =
(CPU Utilization + Memory Utilization) / 2
```

For example:

```text
CPU Utilization    = 10%
Memory Utilization = 20%

Average Utilization =
(10 + 20) / 2

= 15%
```

The average value is used as a simplified indicator of overall resource utilization.

It should not be interpreted as a replacement for detailed workload-specific performance analysis.

---

# 6. Over-Provisioning Threshold

The current implementation uses a **30% utilization threshold**.

The basic logic is:

```text
Average Utilization < 30%
            |
            v
Potential optimization opportunity
```

Workloads below this threshold are flagged for further analysis.

The system does not immediately modify these workloads.

Instead, they are passed to the optimization engine where waste and potential savings are calculated.

---

# 7. Why a 30% Threshold?

The threshold is intended to identify workloads with substantial unused requested capacity.

For example:

```text
Resource Request = 1.0 CPU
Actual Usage     = 0.01 CPU

Utilization      = 1%
```

This indicates a significant difference between requested and observed capacity.

A 30% threshold therefore acts as a practical heuristic for the local demonstration environment.

It is not intended to represent a universal Kubernetes right-sizing rule.

---

# 8. Production Considerations for Thresholds

A production-grade optimizer should not rely solely on a single short-term utilization value.

It should consider:

* Historical utilization
* Peak utilization
* CPU percentile values
* Memory percentile values
* Traffic patterns
* Application behavior
* SLO requirements
* Request latency
* Error rates
* Autoscaling behavior
* Safety margins

For example, a workload with an average CPU utilization of 20% may still require a higher CPU request if it experiences regular traffic spikes.

Therefore:

```text
Observed Low Utilization
        !=
Automatically Safe to Resize
```

The current engine should be considered a **recommendation system**, not an autonomous sizing authority.

---

# 9. Waste Calculation

Once an optimization opportunity is identified, the engine calculates the difference between requested and observed resources.

CPU waste:

```text
CPU Waste =
max(CPU Request - CPU Usage, 0)
```

Memory waste:

```text
Memory Waste =
max(Memory Request - Memory Usage, 0)
```

The `max()` operation prevents negative waste values.

---

# 10. CPU Waste Example

Consider:

```text
CPU Request = 1.0 core
CPU Usage   = 0.002 core
```

The waste is:

```text
CPU Waste =
1.0 - 0.002

= 0.998 cores
```

This indicates that approximately 0.998 requested CPU cores were not being consumed at the observed measurement point.

---

# 11. Memory Waste Example

Consider:

```text
Memory Request = 2.0 GB
Memory Usage   = 0.001 GB
```

The waste is:

```text
Memory Waste =
2.0 - 0.001

= 1.999 GB
```

Again, this represents the difference between the requested and observed resources.

---

# 12. Waste Analysis Output

The `analyze_waste()` method enriches each optimization opportunity with:

```text
cpu_waste
memory_waste
```

Example:

```text
{
    "namespace": "default",
    "name": "web-app-79bc9f6b6c-td285",

    "cpu_request": 1.0,
    "cpu_usage": 0.0001,
    "cpu_waste": 0.9999,

    "memory_request": 2.0,
    "memory_usage": 0.0133,
    "memory_waste": 1.9867
}
```

This normalized information becomes the input for savings estimation.

---

# 13. Savings Calculation

The engine estimates monthly savings using configurable cost assumptions.

The calculation is conceptually:

```text
CPU Savings =
CPU Waste × Monthly CPU Cost
```

and:

```text
Memory Savings =
Memory Waste × Monthly Memory Cost
```

Then:

```text
Total Monthly Savings =
CPU Savings + Memory Savings
```

The cost values are maintained in the project's configuration rather than being hard-coded into the optimization logic.

This makes the optimization engine easier to adapt to different pricing assumptions.

---

# 14. Savings Are Estimates

The estimated savings values generated by the application should not be interpreted as guaranteed GCP billing reductions.

For example:

```text
Estimated Monthly Savings:
₹122.95
```

means that the current model estimates approximately ₹122.95/month of optimization opportunity based on the configured resource-cost assumptions.

Actual cloud savings could be different.

---

# 15. Why Actual Savings Can Differ

Actual GCP savings depend on factors including:

* Kubernetes node capacity
* Node packing
* Cluster autoscaling
* Machine types
* Regional pricing
* Billing model
* Committed-use discounts
* Spot/Preemptible pricing
* Other workloads sharing the node
* Resource limits
* Pod scheduling
* Minimum cluster capacity

For example, reducing a Pod's CPU request may not immediately reduce the number of nodes in a cluster.

Therefore:

```text
Resource Waste
        |
        v
Optimization Opportunity
        |
        v
Potential Savings
```

does not necessarily mean:

```text
Potential Savings
        =
Immediate Billing Reduction
```

# 18. Recommendation Actions

The engine generates different actions depending on workload utilization.

For workloads with very low utilization:

```text
Right-size CPU and memory requests
```

For appropriately utilized workloads:

```text
Maintain current resource allocation
```

For highly utilized workloads:

```text
Monitor; workload is appropriately sized
```

Batch workloads may receive additional guidance.

For example:

```text
Right-size resources and consider Spot instance/node pool
```

---

# 19. Batch Workload Optimization

The `batch-worker` workload receives additional optimization consideration.

The recommendation includes:

```text
Right-size resources and consider Spot instance/node pool
```

The reasoning is that batch workloads may sometimes be suitable for lower-cost compute capacity when the workload can tolerate interruption.

This is a recommendation only.

The system does not automatically move the workload to Spot capacity.

A production implementation would need to verify:

* Workload restart behavior
* Checkpointing
* Job retry behavior
* Interruption tolerance
* Completion deadlines
* Availability requirements

before implementing such a change.

---

# 20. Priority Assignment

Recommendations receive an implementation priority.

The current logic broadly considers utilization levels.

Conceptually:

```text
Average Utilization >= 80%
        |
        v
Low Priority
```

For workloads with lower utilization:

```text
Average Utilization < 30%
        |
        +-----------------------------+
        |                             |
        v                             v
Very low utilization            Moderate low utilization
        |                             |
        v                             v
High Priority                   Medium / High Priority
```

The exact recommendation priority is determined by the implementation logic in `optimizer_engine.py`.

---

# 21. Priority Score

In addition to the High/Medium/Low priority label, the engine calculates a numerical priority score.

The score combines:

* Resource waste
* Utilization
* Estimated savings

Conceptually:

```text
Lower Utilization
       +
Higher Savings
       +
Higher Waste
       |
       v
Higher Priority Score
```

The implementation calculates a waste factor:

```text
Waste Factor =
100 - Average Utilization
```

The score then incorporates the estimated savings contribution.

The final score is bounded to a maximum of 100.

---

# 22. Why Use Both Priority and Priority Score?

The human-readable priority:

```text
High
Medium
Low
```

is easy to understand.

The numerical priority score provides a more granular ranking.

For example:

```text
Workload A
Priority: High
Score: 75.01

Workload B
Priority: High
Score: 72.96

Workload C
Priority: High
Score: 72.38
```

All three workloads can therefore be considered high priority while still being ordered by score.

# 30. Why the Results Can Change

Prometheus measures live workload activity.

Therefore, the values can change between two executions.

For example:

```text
Run 1:
high-cpu-app CPU = 30.47%

Run 2:
high-cpu-app CPU = 32.9%
```

This is expected behavior.

The workload's observed CPU usage is not a fixed property.

It depends on:

* Current workload activity
* CPU scheduling
* Background processes
* Measurement interval
* Prometheus query window

Therefore, the optimization engine should be evaluated based on the overall behavior of the pipeline rather than expecting every execution to produce identical values.

# 32. Relationship Between Analysis and Execution

An important architectural principle is that recommendation generation and Kubernetes modification are separate stages.

```text
                ANALYSIS
                   |
                   v
          Optimization Engine
                   |
                   v
             Recommendation
                   |
                   |
             Human Review
                   |
                   v
                EXECUTION
                   |
                   v
             ActionExecutor
                   |
                   v
             Kubernetes
```

This separation is important because a recommendation does not automatically mean that a workload should be modified.

---

# 33. Right-Sizing Safety

The current engine uses observed utilization to identify opportunities.

It does not automatically reduce resource requests to the exact observed usage.

For example, if:

```text
Actual CPU = 0.0001 cores
```

the system does not assume that:

```text
CPU Request = 0.0001 cores
```

is automatically safe.

A production right-sizing system should apply a safety margin.

Conceptually:

```text
Historical Peak
      |
      v
Percentile Analysis
      |
      v
Safety Margin
      |
      v
Recommended Request
```

This prevents recommendations from being overly aggressive.

# 35. Current Limitations

The current optimization engine has several deliberate limitations.

## Mock Cost Data

The local environment does not retrieve actual GCP billing data.

The cost layer uses mock data.

---

## Short-Term Utilization

The current analysis is based on currently observed Prometheus usage rather than long-term historical behavior.

---

## Simplified Threshold

The 30% threshold is a heuristic.

It does not account for workload-specific requirements.

---

## Simplified Savings Model

The savings calculation is based on configurable resource cost assumptions.

It does not model the complete GCP billing system.

---

## No Automatic Right-Sizing

The project generates recommendations but does not automatically apply aggressive resource reductions.

The ActionExecutor is configured for safe dry-run behavior.

---

Store and analyze longer periods of Prometheus metrics.

Use metrics such as:


Identify workload spikes before recommending reductions.

### Workload-specific thresholds

Use different optimization policies for:

* Critical services

Combine resource utilization with:

* Latency

Analyze workloads across multiple Kubernetes clusters.

# 38. Engineering Principles Demonstrated

The optimization engine demonstrates several practical engineering principles.

## Separation of concerns

Metrics collection is separated from optimization logic.

## Explainability

Recommendations contain utilization, waste, savings, priority, and reason information.

## Configurability

Cost assumptions and optimization parameters are separated from the core logic.

## Safety

Recommendations are separated from infrastructure execution.

## Testability

Individual stages can be tested independently.

## Extensibility

The cost source can be replaced with a production GCP billing integration without redesigning the optimization engine.
